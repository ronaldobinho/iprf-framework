## Session 4.1 — Resilience assessment model

1. Extend `assessment-engine` (same module, new category depth — do not create a
   separate service) with a resilience input schema capturing:
   - startup/recovery time measurements (a series, not a single number)
   - dependency inventory (count, sync vs async init, sequential chains)
   - database round trips during initialization
   - scaling dimension (what N grows: instruments, accounts, partitions)
   - incident history (recurrence of same root cause = missing permanent remediation)
2. Analyzer: given recovery-time measurements at different values of N, fit
   `startupTime ≈ base + N × cost` (simple linear regression, R² reported). If the
   linear term is significant, report GROWTH COUPLING with the projected recovery
   time at 2×, 5×, 10× current scale.
3. Findings map to the maturity model: coupled recovery that grows with business
   volume caps Resilience/Recovery categories per documented gating rules.

Deliverable: a synthetic dataset with deliberate linear coupling produces the
coupling finding with projection table; an uncoupled dataset does not.

## Session 4.2 — Remediation modeling + sample

1. Remediation simulator: given the coupled profile, model the effect of
   - parallel processing (divide validation cost by worker count, plus overhead)
   - batch validation (N round trips → N/batchSize)
   - removing unnecessary sequential dependencies (critical-path reduction)
   and output projected recovery times per intervention and combined.
2. `samples/resilience-meridian/`: the sample institution's resilience input +
   generated report showing before/after projections. All numbers SYNTHETIC,
   generated by the simulator itself — never hand-typed results.
3. Wire resilience results into the Phase 3 report as its Resilience/Recovery/
   Scalability sections.

Deliverable: sample resilience report committed, projections reproducible from input.

## Session 4.3 — Case study + docs

1. `docs/framework/case-study-recovery-time.md`:
   - Problem: critical financial infrastructure with ~30-minute initialization
   - Root cause: sequential per-instrument validation + excessive DB round trips
   - Interventions: parallel processing, batch validation, removal of unnecessary
     sequential dependencies
   - Outcome: ~80% recovery-time reduction
   - MANDATORY framing (verbatim intent): this is the founder's documented
     professional experience that motivated the methodology — it is NOT a result
     produced or reproduced by this repository. The repository's simulator
     demonstrates the same class of remediation on synthetic data.
   - Closing lesson: "Growth should not silently become a recovery-time multiplier."
2. Update `resilience-model.md` and `growth-coupling.md` to reference the
   implemented analyzer (docs/engine reconciliation, as in Phase 3).
